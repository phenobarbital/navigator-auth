navigator-auth · Identity Vault

Sign in (Basic, this app's own OAuth2, or SSO), then link external accounts so navigator-auth stores their credentials — ciphered — and other systems can act on your behalf without ever seeing a token.

1 · Sign in — create a Navigator session

Basic — POST /api/v1/login

navigator-auth OAuth2 — Authorization Code + PKCE

This same application is the Authorization Server. The flow goes through /oauth2/authorize and /oauth2/token; the access token it returns is bound to the session it creates, so the vault endpoints below accept it too.

Single sign-on — external backends

GET /api/v1/auth/{provider}/ — the provider authenticates you and navigator-auth creates (or reuses) the matching auth.users row.

Session — GET /api/v1/me

2 · Link an identity — /api/v1/user/identities/link/{provider}

A second OAuth2 authorization, run while you are already logged in. It does not touch your session: it captures an access + refresh token (with the provider's identity scopes) and stores it ciphered in auth.user_identities.

3 · Linked identities — GET /api/v1/user/identities

Provider Account Scopes Status Actions
Open the management page ↗

Tokens are never listed here — the API returns them masked. The management page (/api/v1/user/identities/manage) is the same data rendered server-side by navigator-auth itself.

4 · Use a linked credential

GET /api/v1/demo/whoami/{provider} is a plain server-side handler: it asks the IdP for your stored credential (refreshing it if it expired) and calls the provider's API with it — no browser, no interactive flow. The credential endpoint below is the HTTP equivalent for out-of-process consumers.
