## 1. Motivation & Business Requirements

### Problem Statement

FEAT-106's review-fix spec (`sdd/specs/basicauth-otp-2fa-review-fixes.spec.md`) shipped two OAuth2
security changes whose tests never touched a real database, a real Redis or a real token:

- **TASK-184** (spec M6, "OAuth2 password form enforces the second factor"). Its Test
  Specification asked for an `oauth_live` fixture on live Postgres + Redis, an e-mail OTP check
  ("an email-preferred user receives exactly one OTP email"), a challenge replay check, and the
  **AC10** OAuth rows (`/oauth2/login` and `/oauth2/login/mfa` finish within 10 s against
  `single_connection_authdb`, with no `acquire()` while `LOCK_CONNECTION` is set). Its Completion
  Note records the deviation: *"the live-Postgres AC10 single_connection_authdb test and live
  email-OTP/replay checks … were not written; tests are mock-based. Follow-up needed."*
  `tests/test_mfa_review_fixes_oauth2.py` drives `Oauth2Provider` with a stubbed
  `SecondFactorGate` (`_FakeGate`) and stubbed lease, so the real gate, OTP delivery, challenge
  store and lock behaviour are never exercised on that path.
- **TASK-187** (spec M9, request-local bearer assurance for ABAC). Its Completion Note records:
  *"no real end-to-end OAuth token-minting test (unit-level with fake request)"*. AC27 and AC29
  in `tests/test_mfa_review_fixes_oauth2_tokens.py` feed hand-written claims into
  `bearer_context_from_claims` and a `_FakeRequest`. Nothing proves that a token actually minted by
  `/oauth2/token` after a real TOTP / trusted-device / password-only browser login carries the right
  claims, passes the real `_auth_middleware`, and is evaluated by `EvalContext` without borrowing the
  identity-shared session's assurance.

The mocks prove the adapters' wiring. They do not prove the security properties end to end. In
particular, AC10 is a deadlock property and AC29 is a cross-token isolation property; both can only
fail against real pools and real shared sessions.

### Goals

- **G1** — One reusable live OAuth2 harness: a real `AuthHandler(BasicAuth + Oauth2Provider)`
  application on live Postgres + Redis with `AUTH_BASIC_2FA_ENABLED`, driven over HTTP.
- **G2** — Live TASK-184 coverage: e-mail OTP delivery (exactly one), challenge single-use (replay
  fails), the stored browser auth-event record, and the AC10 OAuth rows on a one-connection `authdb`.
- **G3** — Live TASK-187 coverage: AC27 and AC29 with access tokens minted by the real
  `/oauth2/authorize` → `/oauth2/token` (PKCE S256) path and evaluated through the real bearer
  middleware and `EvalContext`.

### Non-Goals (explicitly out of scope)

- Any change to production code under `navigator_auth/`, `templates/` or `scripts/`. If a live test
  exposes a production defect, the task records it and the defect is filed as a new ledger issue —
  it is not fixed inside this feature.
- Replacing or deleting the existing mock-based tests. They stay as fast adapter-level coverage.
- Device-flow, refresh-chain, introspection and userinfo assurance (AC23–AC26 of the parent spec).
- The AC10 rows that are not OAuth (`BasicAuth`, `/auth/mfa/verify`, password change/reset, passkey,
  disenroll, backup codes) — already covered elsewhere.
- Performance tuning beyond the 10 s AC10 budget.

## 2. Architectural Design

### Overview

Tests only. The live harness reuses the proven BasicAuth live harness in `tests/test_mfa_e2e.py`
(`Live`, `_patch_settings`, `_stop`, `requires_fresh_factor`, the e-mail OTP capture), and adds:

1. an application factory that registers **both** `navigator_auth.backends.BasicAuth` (owner of the
   MFA slot, spec D4) and `navigator_auth.backends.Oauth2Provider`, and optionally lets the caller
   install its own `app["authdb"]` pool before startup (for AC10);
2. a test-only bearer route that builds `EvalContext` exactly like the PDP and reports the effective
   assurance, the raw session assurance and `requires_fresh_factor`;
3. an `OAuthLive(Live)` helper class that speaks the browser leg of OAuth2 over HTTP (password
   form, MFA form, authorize, token exchange) with explicit cookies — never the client jar.

After `on_startup`, the harness swaps `Oauth2Provider.client_storage` for a `MemoryClientStorage`
holding one public PKCE client, and pre-seeds an `OauthGrant` for each test user so `/oauth2/authorize`
issues the code directly (consent is not under test). Everything else — gate, MFA services,
challenge store, OTP provider, auth-event store, code/token/grant/access-token storages, session
storage, `authdb` locks — is the real thing.

### Component Diagram

```
pytest ──HTTP──▶ TestServer(app)
                  ├─ AuthHandler._auth_middleware ──▶ /_test/oauth/evalctx ──▶ EvalContext ──▶ requires_fresh_factor
                  ├─ BasicAuth  (/api/v1/login, /auth/mfa/*)  ── owns MFA slot (MfaServices)
                  └─ Oauth2Provider
                       /oauth2/login ──▶ SecondFactorGate.decide ──▶ challenge page | session + auth event
                       /oauth2/login/mfa ──▶ SecondFactorGate.verify ──▶ 302 /oauth2/authorize + cookies
                       /oauth2/authorize ──▶ _issue_code (grant pre-seeded) ──▶ 302 redirect_uri?code=
                       /oauth2/token ──▶ _handle_authorization_code ──▶ access_token {mfa?, amr?}
live Postgres (authdb, users, tenant policy, generation)   live Redis (sessions, events, codes, challenges)
```

## 5. Acceptance Criteria

> This feature is complete when ALL of the following are true:

- [ ] **AC1** — Live, 2FA on, enforced tenant, user without TOTP: `POST /oauth2/login` with the
      right password returns 200 HTML (the MFA form), `Cache-Control: no-store`, no session
      `Set-Cookie`, no `Location`; exactly one e-mail OTP is captured for that user, addressed to
      the user's e-mail, and the code does not appear in the payload's `repr`.
- [ ] **AC2** — `POST /oauth2/login/mfa` with that code returns 302 to `/oauth2/authorize` carrying
      the 9 authorize parameters exactly as submitted. Re-posting the same challenge and code
      returns no 302, sets no session cookie, and renders the login page with an error.
- [ ] **AC3** — The event cookie set on that 302 names a Redis record (key
      `OAUTH2_EVENT_KEY_PREFIX + sha256(handle)`) holding the user's id, `mfa: true` and
      `amr: ["pwd", "otp"]`. The raw handle never appears in the key.
- [ ] **AC4** — AC10 OAuth rows: with the application's `authdb` replaced by the strict
      `single_connection_authdb` before startup, `POST /oauth2/login` (challenge) and
      `POST /oauth2/login/mfa` (success) each finish within 10 s with the expected status
      (200 and 302), and `single_connection_authdb.acquires_inside_lock == []`.
- [ ] **AC5** — AC27 end to end: access tokens minted through `/oauth2/authorize` → `/oauth2/token`
      (PKCE S256) after (a) a TOTP login, (b) a trusted-device login and (c) a no-factor-owed login
      carry `mfa`/`amr` claims `True`/`["pwd","totp"]`, `True`/`["pwd","trusted_device"]` and none,
      respectively. A bearer request with each token through the real `_auth_middleware` yields
      `requires_fresh_factor` True for (a) only.
- [ ] **AC6** — AC29 end to end, for one user:
  - a password-only token minted **before** a TOTP mint, and a trusted-device token minted
    **after** one TOTP mint and **before** another, both evaluate as not fresh;
  - this holds while the identity-shared session holds a later BasicAuth TOTP login's assurance.
    The test asserts this precondition (raw session `mfa` true, `amr` contains `totp`) so it cannot
    pass vacuously;
  - both TOTP tokens evaluate as fresh;
  - after the session's Redis keys are deleted, each token's first request recreates the session
    from the token and every result is unchanged.
- [ ] **AC7** — Without Postgres, Redis, MFA services or a Vault keyring, every new live test
      **skips** (never fails), exactly like `tests/test_mfa_e2e.py::live`.
- [ ] **AC8** — `tests/test_mfa_review_fixes_oauth2.py`, `tests/test_mfa_review_fixes_oauth2_tokens.py`
      and `tests/test_mfa_e2e.py` pass. `git diff --name-only` for the feature lists only files
      under `tests/` (plus SDD state). No production code changes.
- [ ] **AC9** — No lint errors on the changed test file (`ruff check` if configured, otherwise
      `flake8`). Each new test docstring names the parent AC it covers (FEAT-106 AC1/AC2/AC10/AC27/AC29).

## 7. Implementation Notes & Constraints

### Patterns to Follow

- Mirror `tests/test_mfa_e2e.py::live` exactly for settings, skip conditions and teardown:
  `_patch_settings(monkeypatch, enabled=True, secret=mfa_secret)`, then override
  `conf.AUTHENTICATION_BACKENDS` to `OAUTH_BACKENDS`. Skip on start failure, on unavailable MFA
  services and on a missing `app["vault_keyring"]`. Freeze the TOTP clock and repoint the e-mail
  provider callback to `"tests.test_mfa_e2e._capture_otp"` after startup. Clear `CAPTURED` before
  and after.
- In `_start_oauth`, after `client.start_server()`, also do the `_start` post-start steps: set
  `backend._callbacks = None` on **both** backends (production success callbacks reach unavailable
  services), and replace `client_storage` with a `MemoryClientStorage` holding
  `OAuthClient(client_id=OAUTH_CLIENT_ID, client_name=..., client_type="public",
  redirect_uris=[OAUTH_REDIRECT], default_scopes=["default"])`.
- Cookies are always explicit (`Live._no_jar()` before every request). Requests that must not
  follow redirects use `allow_redirects=False`. Session and event cookies are read from the
  response's `Set-Cookie` (`response.cookies`) and passed on the next hop.
- Use a real PKCE pair: `verifier = secrets.token_urlsafe(48)`,
  `code_challenge = generate_challenge(verifier)`, method `S256`.
- The bearer test route must not be in the auth exclude list, so `_auth_middleware` runs and
  publishes `AUTH_BEARER_CONTEXT_KEY`. It returns `ctx.mfa`, the effective `amr` from
  `ctx.userinfo`, `requires_fresh_factor(ctx)`, and the raw session `AUTH_SESSION_OBJECT`
  `mfa`/`amr` (the AC6 precondition). Read the raw values with `.get()`; an OAuth-created session
  may have no `AUTH_SESSION_OBJECT`.
- AC4 (AC10): construct `AuthHandler(..., enable_authdb=False)`, set
  `app["authdb"] = single_connection_authdb` **before** startup, then
  `single_connection_authdb.strict = True` once startup is done (startup itself legitimately
  acquires). Wrap each HTTP call in `asyncio.wait_for(..., 10)`. The test data helpers (`Live.user`,
  `Live.org`) use the separate `mfa_db` pool.
- AC6 ordering (sessions are identity-shared and a later `new_session` overwrites the data):
  1. tenant OFF, no TOTP → OAuth login with no factor owed → mint `pwd`;
  2. enrol TOTP through BasicAuth (`plain_login` + `enrol_totp`);
  3. OAuth TOTP login with `remember_device` → mint `totp1`, keep the trusted cookie;
  4. OAuth login with the trusted cookie → mint `trusted`;
  5. OAuth TOTP login without the trusted cookie → mint `totp2`;
  6. **last**, BasicAuth TOTP login (`totp_login`) for the same user, so the shared session holds
     TOTP assurance; assert the precondition through the route;
  7. evaluate all four tokens; delete `session:<sid>` / `user:<username>` through the session
     storage's Redis pool; evaluate all four again.
  Use `live.totp(secret)` for every code. It advances the frozen clock, so the TOTP replay guard
  never trips.
- Google-style docstrings on helpers. Never print or log OTP codes, tokens or cookies.

### Known Risks / Gotchas

- **Unclosed pools**: `Oauth2Provider.flow_store` builds its own Redis pool lazily and the app does
  not close it. The fixture teardown must `await provider._flow_store._pool.disconnect()` (or the
  equivalent attribute; verify before use), or pytest-asyncio's per-test loop may hang or warn.
- **Short local JWT secret**: `pytestmark` must ignore `jwt.warnings.InsecureKeyLengthWarning`
  (same as `tests/test_mfa_e2e.py:80`) or strict warnings fail the test.
- **Postgres OAuth storages**: `OAUTH2_CLIENT_STORAGE` defaults to `postgres` for clients and
  `get_*_storage(storage_type, ...)` for grants/tokens. Only the client storage is swapped. Grant
  and access-token storages use whatever the environment configures. Use the provider's own
  `grant_storage` instance to seed grants, never a new one.
- **Known flaky neighbour**: `tests/test_mfa_e2e.py` showed one non-reproducible failure in a first
  run on 2026-11-11 (passed on re-run). Treat a single failure there as pre-existing unless it
  reproduces.
- If a live test exposes a production defect (AC10 nested acquire, assurance borrowing), do not
  fix production code here: mark the test `xfail(strict=True, reason="issue:<id>")`, file the
  defect with `wikitoolkit ledger open`, and record it in the Completion Note.
