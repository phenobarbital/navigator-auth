## Additional findings

1. **High — trusted-device login is not serialized with security transitions.** [basic.py:366](navigator_auth/backends/basic.py:366) evaluates policy and rotates a device before opening a session without the per-user lock used by [events.py:47](navigator_auth/mfa/events.py:47). For example, a password reset can revoke devices after rotation but before the pending login opens its session, allowing a session based on the old password and device after the reset. Hold the same user lock across fresh credential/context validation, device consumption, and session creation; coordinate policy changes as well.

2. **High — passkey changes can commit despite a failed MFA transition.** [passkey.py:320](navigator_auth/backends/passkey.py:320) and [passkey.py:569](navigator_auth/backends/passkey.py:569) wrap store operations in `security_transition`, but [store.py:121](navigator_auth/passkey/store.py:121) acquires its own connection for deletion. If the later version bump, device revocation, audit, or lock-transaction commit fails, the passkey removal can persist while the associated security state rolls back. Registration has the same separate-store pattern. Make the credential mutation use the transition connection and transaction.

3. **Medium — factor-management password and proof attempts lack rate limiting.** [mfa.py:294](navigator_auth/handlers/mfa.py:294), [mfa.py:385](navigator_auth/handlers/mfa.py:385), and [mfa.py:436](navigator_auth/handlers/mfa.py:436) repeatedly check a supplied password, and disenrollment also checks TOTP or backup proof, without the limiter used by verification and enrollment confirmation. A stolen authenticated session can be used for online password or factor guessing against these endpoints. Apply user and IP limits before these checks, including failed strong-factor proofs.

4. **Medium — policy hardening can race with a pending password login.** [basic.py:366](navigator_auth/backends/basic.py:366) reads the current policy, then [basic.py:350](navigator_auth/backends/basic.py:350) opens a session when no factor was owed. Meanwhile, [policy.py:122](navigator_auth/mfa/policy.py:122) can enforce MFA and revoke devices without synchronizing with that login’s decision. A login that evaluated the old policy can therefore create a password-only session after enforcement commits. Coordinate policy transitions with login decisions or revalidate the policy under a serialization mechanism immediately before session issuance.

## Merge recommendation

Do not merge yet. The vault rotation incompatibility, connection-pool deadlock risk, and non-atomic credential/security transitions need fixes before this can safely protect production accounts. The trusted-device and policy races also need a consistent synchronization design, and the OAuth2 local-password bypass should be documented prominently or addressed in a follow-up with an explicit deployment constraint. This was a static review; I did not run tests.
