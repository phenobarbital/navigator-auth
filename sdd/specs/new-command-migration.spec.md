# Feature Specification: `navauth self upgrade` — database migration command

**Feature ID**: FEAT-110
**Date**: 2026-11-11
**Author**: Jesus Lara
**Status**: draft
**Target version**: next minor release (0.30.0 expected; currently 0.29.0)

## 1. Motivation & Business Requirements

### Problem Statement

navigator-auth changes its tables (`auth.user_identities`, the vault tables, the
passkey tables, `auth.clients`) through SQL files that are applied in three
different ways, none of them dependable:

- **Vault and identity** SQL runs on every application boot from
  `AuthHandler.auth_startup`, with the runtime database user, and failures are
  only logged. A database whose runtime user cannot run DDL, or that hit a lock
  timeout, stays behind silently. This is the most likely reason a local
  `auth.user_identities` lacks recent columns.
- **Passkey** SQL runs only when that backend is enabled.
- **OAuth2** changes (`navigator_auth/backends/oauth2/ddl.sql`, 284 lines
  touching `auth.clients`, `auth.policies` and six OAuth tables) are loaded by
  no code at all: someone has to find the file and run it by hand.

On top of that, the three runners are copies of each other, each keeps a
hand-written file list (a file that is not listed never runs — this already
happened with identity `006`), nothing records what a database has received,
and asyncdb's `conn.execute()` returns errors instead of raising, so the
runners can report success without applying anything.

The request: one command, `navauth self upgrade`, run with admin credentials,
that checks which migrations a database is missing and applies them, with the
SQL changes kept in one documented place.

### Goals

- **G1** — A `navauth` console script with `self upgrade` that applies every
  pending migration, and `self upgrade --check` that only reports.
- **G2** — One migration catalog: all SQL under
  `navigator_auth/migrations/sql/<set>/`, discovered from the filesystem, no
  hand-written file lists.
- **G3** — A ledger table recording each applied file (checksum, time, user,
  package version); SQL files stay idempotent as the safety net.
- **G4** — Fail-closed execution: a failed file is always reported as failed.
- **G5** — Admin credentials for DDL, separate from the runtime `DBUSER`.
- **G6** — Application startup stops running DDL; it checks and warns.
- **G7** — The OAuth2 patch becomes a managed migration.
- **G8** — `docs/migrations/` documents every migration and how to add one.

### Non-Goals (explicitly out of scope)

- Creating the base `auth` schema or its base tables (`auth.users`,
  `auth.clients`, `auth.user_identities` …). They are created by the Navigator
  platform; this command only applies additive changes on top.
- Down / rollback migrations.
- Data migrations and vault key rotation (the `navigator-vault` CLI in
  navigator-session covers those).
- Changing the content of already-released SQL files (identity 001–006,
  vault 001–002, passkey 001). They move; they are not edited.
- Databases other than PostgreSQL.
- MFA tables. They belong to FEAT-106 (TASK-130); see §7 for how that task
  plugs into the catalog.
- Adopting an external migration tool — not evaluated; the proposal went
  straight to a home-grown runner because every SQL file is already idempotent.

## 2. Architectural Design

### Overview

A new package `navigator_auth/migrations/` owns everything about schema
changes:

1. **Catalog** — SQL files live in `navigator_auth/migrations/sql/<set>/`,
   named `NNN_description.sql`. Sets are applied in a fixed order
   (`vault`, `identity`, `passkey`, `oauth2`); files inside a set are applied
   in filename order. Files are discovered by listing the directory, so a new
   file needs no registration. `{schema}` and `{users_table}` placeholders are
   rendered from `AUTH_DB_SCHEMA` / `AUTH_USERS_TABLE`; files that hard-code
   `auth.` pass through unchanged.
2. **Ledger** — table `<AUTH_DB_SCHEMA>.schema_migrations`, one row per applied
   file, keyed by `(migration_set, filename)`. A file is `applied` when a row
   with the same checksum exists, `changed` when the row's checksum differs,
   `pending` otherwise. A database without the ledger table has everything
   pending.
3. **Runner** — works on a raw asyncpg connection (which raises on error).
   It takes a session advisory lock, creates the ledger if missing, and for
   each pending file runs the rendered SQL and the ledger upsert inside one
   transaction. A failing file is recorded and the run continues with the
   next file (the behaviour identity migrations already have); the run ends
   with a non-zero exit code naming every failed file.
4. **CLI** — `navauth self upgrade [--check] [--dsn DSN] [--user USER]
   [--set NAME]… [--reapply-changed] [--fail-fast] [-v]`, argparse-based,
   connecting with asyncpg directly.
5. **Startup** — `auth_startup` no longer applies SQL. It reads the ledger
   with the runtime pool and logs one warning listing what is pending. The
   passkey backend keeps failing fast, but on a missing table rather than on a
   failed DDL attempt.
6. **Legacy functions** — `ensure_vault_tables`, `ensure_identity_columns`,
   `ensure_passkey_tables` and their `setup_*` wrappers keep their names,
   signatures and behaviour (apply one set, no ledger) because tests and
   outside callers use them. They lose their private `_run_sql` copies and
   their hand-written file tuples, and gain the fail-closed check.

**First run on an existing database.** A database migrated by earlier startups
has no ledger rows, so everything shows as pending. `navauth self upgrade`
re-runs the idempotent files (no-ops on an up-to-date schema) and records
them. This is why files must stay idempotent.

**Behaviour change for operators.** From the release that ships this feature, new schema
changes are not applied at boot any more. Deployments must run
`navauth self upgrade` (or `--check` in CI). Startup logs a warning until they
do.

### Data Models

```python
class MigrationFile(BaseModel):          # frozen
    migration_set: str                   # "vault" | "identity" | "passkey" | "oauth2"
    filename: str                        # "004_identity_base_columns.sql"
    path: Path
    checksum: str                        # sha256 hex of the raw file bytes

class MigrationState(str, Enum):
    APPLIED = "applied"
    PENDING = "pending"
    CHANGED = "changed"

class MigrationStatus(BaseModel):
    file: MigrationFile
    state: MigrationState
    applied_at: datetime | None = None
    recorded_checksum: str | None = None

class MigrationResult(BaseModel):
    file: MigrationFile
    ok: bool
    error: str | None = None
    duration_ms: int = 0

class UpgradeReport(BaseModel):
    applied: list[MigrationResult]
    failed: list[MigrationResult]
    skipped_changed: list[MigrationStatus]
```

Ledger table (created by the runner, not by a numbered file; `{schema}` is
`AUTH_DB_SCHEMA`):

```sql
CREATE TABLE IF NOT EXISTS {schema}.schema_migrations (
    migration_set   VARCHAR(64)  NOT NULL,
    filename        VARCHAR(255) NOT NULL,
    checksum        CHAR(64)     NOT NULL,
    applied_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    applied_by      TEXT         NOT NULL DEFAULT current_user,
    package_version VARCHAR(32),
    execution_ms    INTEGER,
    PRIMARY KEY (migration_set, filename)
);
GRANT SELECT ON {schema}.schema_migrations TO PUBLIC;
```

`GRANT SELECT … TO PUBLIC` lets the runtime user read the ledger for the
startup check without this feature having to know the runtime role's name; the
table holds file names and checksums only.

### New Public Interfaces

```
navauth self upgrade                 apply every pending migration
navauth self upgrade --check         report applied / pending / changed; change nothing
        --dsn DSN                    admin DSN (highest precedence)
        --user USER                  admin user; password from AUTH_ADMIN_PWD or a prompt
        --set NAME                   restrict to one set; repeatable
        --reapply-changed            also re-run files whose checksum changed
        --fail-fast                  stop at the first failed file
        -v / --verbose               debug logging
```

Exit codes: `0` success (or nothing pending) · `1` `--check` found pending or
changed files · `2` one or more migrations failed · `3` usage, configuration
or connection error.

DSN precedence: `--dsn` → `AUTH_ADMIN_DSN` → `--user`/`AUTH_ADMIN_USER` with
`AUTH_ADMIN_PWD` (or an interactive prompt on a TTY) plus
`DBHOST`/`DBPORT`/`DBNAME` → `default_dsn` with a printed notice that runtime
credentials are being used. The DSN and password are never printed or logged;
the report names only the source ("--dsn", "AUTH_ADMIN_DSN", …), host,
database and user.

### Module 1: Catalog + SQL relocation
- **Path**: `navigator_auth/migrations/__init__.py`, `navigator_auth/migrations/catalog.py`, `navigator_auth/migrations/sql/<set>/`
- **Responsibility**: single source of truth for which migration files exist,
  in what order, and how they are rendered. Moves the nine released SQL files
  with `git mv` (content byte-identical):
  - `navigator_auth/vault/sql/*.sql` → `navigator_auth/migrations/sql/vault/`
  - `navigator_auth/identity/sql/*.sql` → `navigator_auth/migrations/sql/identity/`
  - `navigator_auth/passkey/sql/*.sql` → `navigator_auth/migrations/sql/passkey/`
- **Depends on**: `navigator_auth/conf.py` (`AUTH_DB_SCHEMA`, `AUTH_USERS_TABLE`)
- **Interface Skeleton**:
  ```python
  # navigator_auth/migrations/catalog.py  (new)
  from ..conf import AUTH_DB_SCHEMA, AUTH_USERS_TABLE  # verified: navigator_auth/conf.py:33-34

  SQL_ROOT: Path = Path(__file__).parent / "sql"
  MIGRATION_SETS: tuple[str, ...] = ("vault", "identity", "passkey", "oauth2")
  FILENAME_PATTERN: re.Pattern[str]  # ^\d{3}_[a-z0-9_]+\.sql$

  class MigrationCatalogError(Exception):
      """The files on disk do not form a valid catalog."""

  class MigrationFile(BaseModel):
      """One SQL migration file. Frozen."""
      migration_set: str
      filename: str
      path: Path
      checksum: str

  def set_dir(migration_set: str) -> Path:
      """Directory of a set. Raises MigrationCatalogError for a name not in MIGRATION_SETS."""

  def set_filenames(migration_set: str) -> tuple[str, ...]:
      """Sorted filenames of one set; empty tuple when the set directory does not exist."""

  def discover(sets: Iterable[str] | None = None) -> tuple[MigrationFile, ...]:
      """All files, ordered by MIGRATION_SETS then filename.

      Raises MigrationCatalogError when: a requested set is unknown; a directory
      under SQL_ROOT is not in MIGRATION_SETS; a .sql file does not match
      FILENAME_PATTERN; two files in a set share the numeric prefix.
      """

  def render_sql(sql: str) -> str:
      """Replace {schema} and {users_table}; other text is returned unchanged."""
  ```
  `navigator_auth/migrations/__init__.py` re-exports `discover`, `render_sql`,
  `MigrationFile`, `MIGRATION_SETS` and, from M2, `get_status`, `upgrade`.

### Module 2: Runner + ledger
- **Path**: `navigator_auth/migrations/runner.py`
- **Responsibility**: fail-closed execution, ledger, status and upgrade.
- **Depends on**: Module 1
- **Interface Skeleton**:
  ```python
  # navigator_auth/migrations/runner.py  (new)
  LEDGER_TABLE = "schema_migrations"
  ADVISORY_LOCK_KEY: int = 1102026  # session-level pg_advisory_lock key for an upgrade run

  class MigrationError(Exception):
      """A statement failed, or the database is not usable for migrations."""

  @asynccontextmanager
  async def acquire_raw(db_pool: Any) -> AsyncIterator[Any]:
      """Yield a raw asyncpg connection from an asyncpg or asyncdb pool.

      Handles both acquire() styles (async context manager, awaitable) and
      releases the connection the same way the legacy _run_sql did.
      An asyncdb connection is unwrapped with get_connection().
      """  # get_connection verified: asyncdb/interfaces/abstract.py:66

  async def execute_checked(conn: Any, sql: str, *args: Any) -> Any:
      """conn.execute(sql, *args) that always raises on failure.

      asyncdb returns [result, error] instead of raising; when the return value
      is a 2-item list/tuple whose second item is an exception, raise
      MigrationError chained to it. Any other return value is passed through.
      """

  async def ledger_exists(conn: Any) -> bool:
      """True when <schema>.schema_migrations exists (to_regclass probe)."""

  async def ensure_ledger(conn: Any) -> None:
      """Create the ledger table and its grant. Raises MigrationError when the schema is missing."""

  async def get_status(conn: Any, sets: Iterable[str] | None = None) -> list[MigrationStatus]:
      """State of every catalog file. Read-only: never creates the ledger."""

  async def upgrade(
      conn: Any,
      sets: Iterable[str] | None = None,
      *,
      reapply_changed: bool = False,
      fail_fast: bool = False,
  ) -> UpgradeReport:
      """Apply pending files (and changed ones when reapply_changed).

      Holds pg_advisory_lock(ADVISORY_LOCK_KEY) for the run. Each file: rendered
      SQL + ledger upsert in one transaction. A failure is recorded in
      report.failed and the run continues, unless fail_fast.
      """
  ```
  `conn` is a raw asyncpg connection: `execute`, `fetch`, `fetchval`,
  `transaction()`.

## 7. Implementation Notes & Constraints

### Patterns to Follow

- **Idempotent SQL**: header comment with the FEAT id and rationale;
  `ADD COLUMN IF NOT EXISTS`; `CREATE … IF NOT EXISTS`; anything else inside a
  `DO` block guarded on `to_regclass(...)` or a catalog lookup. Model:
  `004_identity_base_columns.sql`.
- **New SQL files use `{schema}` / `{users_table}`**; released files keep
  their hard-coded `auth.`.
- **Continue past a failed file, report all failures at the end** — the
  behaviour introduced for identity in commit `569383d`.
- **CLI shape**: `main(argv, *, connect=None) -> int` with an injectable
  connection factory, `asyncio.run()` inside `main`, asyncpg imported lazily
  inside the default factory, explicit exit-code constants.
- **Pydantic models** for `MigrationFile`, `MigrationStatus`,
  `MigrationResult`, `UpgradeReport`; Google-style docstrings and type hints
  throughout; module logger `logging.getLogger("navigator.migrations")`.
- **Tests**: fake connection / mocked pool plus SQL-text assertions; no live
  database required for the unit suite.

### OAuth2 conversion rules (Module 4)

`navigator_auth/backends/oauth2/ddl.sql` cannot be copied as is:

1. **Drop all seed/test data.** The file sets
   `client_secret = 'test_client_secret'` (and test redirect URIs, grant types,
   scopes, expiry) on every row `WHERE client_secret IS NULL` — twice (lines
   44-51 and 86-93). Public clients legitimately have a NULL secret, so a
   managed migration carrying this would overwrite real clients with a known
   secret. None of those `UPDATE`s is carried over.
2. **`NOT NULL` columns on a populated table**: `client_name VARCHAR(255) NOT
   NULL` (line 8) fails when rows exist and the column does not. Use: add
   nullable → backfill (`client_name = client`) → `SET NOT NULL` inside a
   guarded block that skips (with `RAISE NOTICE`) when NULLs remain. Columns
   with `NOT NULL DEFAULT …` (`client_type`, `registration_source`,
   `enforce_access_gate`) are safe as written.
3. **Constraint**: `DROP CONSTRAINT IF EXISTS clients_client_uid_key` followed
   by `ADD CONSTRAINT` (lines 70-74) rebuilds a unique index on every run.
   Replace with a `pg_constraint`-guarded add.
4. **Keep the idempotent backfills** that only fill NULLs from other columns:
   `client` ↔ `client_name`, `client_uid`, `registration_source`.
5. **Duplicated blocks** (lines 76-93 repeat 39-51) appear once.
6. **Every statement is guarded on the table's existence** with
   `ALTER TABLE IF EXISTS` or `to_regclass`, so the file is a no-op on a
   database without `clients` / `policies` rather than an error.
7. **Coverage** — the new file must still create or alter all of:
   `clients` columns `client`, `client_name`, `client_type`, `client_secret`
   (nullable), `redirect_uris`, `policy_uri`, `client_logo_uri`, `user_id`
   (nullable FK), `default_scopes`, `allowed_grant_types`, `is_active`,
   `expiration_date`, `created_at`, `updated_at`, `client_uid`,
   `token_endpoint_auth_method`, `registration_source`,
   `enforce_access_gate`; `policies.scopes`; tables `oauth_refresh_tokens`,
   `oauth_grants`, `oauth_access_tokens`, `oauth_device_codes`,
   `client_access`; and every `CREATE INDEX` in the old file. The task reads
   lines 95-215 of `ddl.sql` (not reproduced here) for the exact table bodies.

### Known Risks / Gotchas

- **asyncdb `execute()` never raises** (returns `[result, error]`). The runner
  uses the raw asyncpg connection; the legacy shims use `execute_checked`.
  This also changes the legacy `ensure_*` functions from silently succeeding
  to raising on a real failure — intended, and it is why `setup_*` wrappers
  stay as the log-only variants.
- **Startup no longer migrates.** Deployments that relied on boot-time
  migration stay behind until someone runs the command. Mitigation: startup
  warning, CHANGELOG entry, `--check` exit code `1` for CI.
- **Pre-ledger databases** show everything as pending once. The first
  `navauth self upgrade` re-runs idempotent files and records them.
- **`006_identity_drop_legacy_uid.sql` removes a column.** It keeps its catalog
  guards untouched; operators should run `--check` first. Nothing in this
  feature weakens the guard.
- **Optional-feature tables are applied to every database** (passkey now,
  MFA later). Decided in the proposal; `--set` lets an operator restrict a run.
- **Runtime user and the ledger**: the startup check needs `SELECT` on the
  ledger and `USAGE` on the schema. The grant to `PUBLIC` covers the table; if
  the check still fails it logs "could not verify" and startup continues.
- **Advisory lock** is session-level, so the whole run must use one
  connection. The CLI holds a single asyncpg connection; never run the upgrade
  through a pool that may hand out different connections.
- **Transactions**: no SQL file contains transaction-control statements today.
  A future file that needs `CREATE INDEX CONCURRENTLY` cannot run inside the
  per-file transaction; the README must say so, and such a file is out of
  scope here.
- **Importing `navigator_auth.migrations.cli` imports `navigator_auth`**, which
  loads `navigator_auth.conf` (navconfig) and `AuthHandler`. The command must
  therefore run in an environment where the application's settings resolve,
  the same as the app itself.
- **`filterwarnings = error`**: constructing `asyncdb.AsyncPool("pg", …)` emits
  a `FutureWarning` from `google.api_core` and turns live-DB tests into skips.
  The live integration test uses `asyncpg.connect` directly.
- **FEAT-106 TASK-130** plans `navigator_auth/mfa/migrations.py` and
  `navigator_auth/mfa/sql/001_mfa_tables.sql`. Whichever feature lands second
  must adapt: with FEAT-110 merged, the MFA SQL goes to
  `navigator_auth/migrations/sql/mfa/` and `"mfa"` is appended to
  `MIGRATION_SETS` (the `test_every_sql_dir_is_registered` test will fail
  otherwise, which is the point).
- **Docs and SQL comments mention old paths** (`passkey/migrations.py`,
  `identity/sql/…` in `documentation/identity-vault.md` and in SQL headers).
  SQL file content is frozen; prose docs are updated in M7 where they name a
  moved path.
- **Line-ending / checksum stability**: checksums are computed over raw bytes;
  `.gitattributes` normalisation on Windows checkouts would change them. The
  `changed` state is a warning, not an error, for this reason.

## Worktree Strategy

- **Isolation**: one feature worktree for FEAT-110; the `sdd-coder` engine
  gives each task its own sub-worktree inside it.
- **Module dependency graph**:
  - M2 → M1 (imports `discover`, `render_sql`, `MigrationFile`)
  - M3 → M1 (`set_dir`, `set_filenames`; the SQL files it points at are moved by M1) and → M2 (`execute_checked`)
  - M4 → M1 (the `oauth2` set directory and the catalog tests)
  - M5 → M2 (`get_status`, `upgrade`, `MigrationError`)
  - M6 → M2 (`get_status`, `acquire_raw`)
  - M7 → M1, M4, M5 (documents the final file list and the CLI)
  - M3, M4, M5 and M6 have no edges between them and can run concurrently once
    their prerequisites are merged.
- **Shared files**: none between concurrent modules. `pyproject.toml` and
  `navigator_auth/conf.py` are touched only by M5; `navigator_auth/auth.py`
  and `navigator_auth/backends/passkey.py` only by M6; the three legacy
  `migrations.py` only by M3; `navigator_auth/migrations/__init__.py` is
  created by M1 and extended by M2 (serialized by the M2 → M1 edge).
- **Exclusive resources**: the `git mv` of the nine SQL files (M1) changes
  paths every other module reads — M1 must be merged before any other module
  starts. No extension rebuild, lockfile or database is mutated by the tasks.
- **Cross-feature dependencies**: none required. FEAT-106 (TASK-130) overlaps;
  see §8.
